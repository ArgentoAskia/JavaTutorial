## Java Time API

在`Java`中早期，表示时间常用`Date`、`Calendar`、`TimeZone`这三个类，这些类在`java.utils`包下，由于历史原因，数据库编程用到的`Time`、`Date`、`Timestamp`也是基于这些类来制作。

但是这些类处理时间都过于简单，`JDK 8`以后，引入了`java.time`包来专门处理时间：

- `java.time`包：新的`Java`日期/时间`API`的基础包，内部包括了很多

- `java.time.chrono`为非`ISO`的日历系统定义了一些泛用的`API`（如日本帝国历、佛历、民国历等）
- `java.time.format`：格式化和解析日期时间对象的类

- `java.time.temporal`：包含一些时态对象还有各类时间操作接口，可以用其找出关于日期/时间对象的某个特定日期或时间
- `java.time.zone`：包含支持不同时区以及相关规则的类

### 相关时间概念

地球的自转产生了昼夜更替，影响了我们的活动，我们很容易就想到使用一种线性结构来表示"我们在时间刻上的活动"，类似一条长长的电影胶片一样，所有的时刻在这条无限长的线上组成有序的集合体，这条线有个很好听的名字，叫**时间线**（`timeline`）。

然而要具体表达时间线上的某一点并非易事，原因在于难以确定标准（例如在力学上，牛顿给出了托起两个鸡蛋用的力就是1牛，但我们说的1秒到底有多长？）。在古代，科技没有那么发达，人们通过立杆测影发现正午影长最短，西周已用圭表确定冬至、夏至；日晷将晷面均分 12 份，形成"十二时辰"，每时辰 2 小时，对应地支子、丑、寅……亥，而在中世纪，机械的发展诞生了**惠更斯摆钟**、**航海钟**等初步计时工具，由此普及，形成"时-分-秒"三级指针。

而在1884年，华盛顿国际子午线会议将格林尼治子午线定为 0°，地球每 15° 划分 1 个时区，形成"时区时间"——地方时让位于区域统一时刻，自此，`GMT`（格林尼治平太阳时，**Greenwich Mean Time**，0° 所在地伦敦郊区格林威治天文台的**平均太阳时**）成为了统一时间，这是人类史上首次时间统一，国际电报、列车时刻表都采用`GMT`作为时间标准。

`GMT`将全世界划为`24`个时区，分东边西边两侧12个时区，每个时区之间相差一个1小时，以0°为基础往西边走一个时区减少一个小时，往东边走一个时区增加一个小时，比如当前0°的时间为`2025-10-24 05:59:02`，则西2区时间为`2025-10-24 03:59:02`（减2个小时）东`8`区为`2025-10-24 13:59:02`（加8个小时），基于这种方式我们可以这样标示时间：2025-10-24 03:59:02 -2（当前地点的时间，后面的-2代表当前时区是西2区），我们可以通过这个[网站](https://www.beijing-time.org/shiqu/)查看全世界时区时间。

在1920s 年代，石英晶体发现后，石英钟揭示地球自转存在毫秒级季节性波动，**天文秒不再恒定**。而GMT靠观测太阳，**不做闰秒**，**未考虑地球形状与轨道椭圆效应**。在高纬度或跨越 >90° 经度时，地方太阳时与 GMT 的偏差可达 **数十分钟**（极端地区 >30 min）。**1967**年国际计量大会定义：**1 秒 = 铯-133 基态两超精细能级跃迁对应辐射的 9 192 631 770 个周期**。由此诞生 **TAI（国际原子时）** —— 完全脱离天文现象（到此时，时间基本有了最基础的单位标准，但实际上此时仍然没看完全脱离），以原子钟组为基准，原子秒自此诞生。

然而地球自转是不均匀的，为兼顾地球自转，在 TAI 上插入闰秒，形成当今全世界通用的**UTC（协调世界时）**。

````
闰秒
闰秒（leap second）是**人为插入（或删除）到 UTC（协调世界时）的 1 秒钟**，目的是让基于原子振荡的 UTC 与基于地球自转的 UT1（天文世界时）之差不超过 0.9 秒。它并非自然天体事件，而是**国际地球自转与参考系服务（IERS）**根据地球自转速率变化宣布的**历法修正**。
当 UT1（天文时）与 UTC 相差 > 0.9 s，插入 1 闰秒，保证太阳仍在 12:00 过中天。
---

### 一、为什么需要闰秒？

1. **地球自转不均匀**  
   潮汐摩擦、地核角动量交换、冰川/海水质量再分布等使地球日长度**长期增加**（每世纪约 +1.7 ms），并叠加**季节性波动**（±0.5 ms）和**不可预测突变**（地震、季风）。  
   → 天文日（UT1）与原子日（TAI）逐渐偏离。

2. **UTC 的定义**  
   1967 年：1 秒 = 铯-133 原子跃迁 9 192 631 770 周期 → **TAI**（国际原子时）恒定。  
   1972 年：引入 **UTC = TAI + 闰秒偏移**，保持 |UTC − UT1| < 0.9 s。

---

### 二、闰秒规则与流程

| 要点 | 内容 |
|---|---|
| **决策机构** | IERS（巴黎）https://iers.org |
| **公告时间** | 每年 1 月/7 月发布；**插秒必须在 6 月 30 日或 12 月 31 日**（偶尔 3 月、9 月）。 |
| **插入形式** | `23:59:60` 出现一次，随后才跳 `00:00:00`。 |
| **删除形式** | 理论上 `23:59:58` 后直接 `00:00:00`（**至今未执行过**）。 |
| **偏移量** | 每插入 1 秒，UTC − TAI = +1 s；**累计 37 秒**（1972-2025）。 |

**最新一次**：2016-12-31 23:59:60（UTC）。  
**下一次**：尚未公告（2025-06 暂无插秒）。

### 四、对各行业的影响

1. **计算机 & 操作系统**  
   - Linux `ntpd`/`chronyd`：跳秒模式（clock jump）或 **slewing**（平滑漂移）。  
   - Windows：采用 **slewing**，系统时钟 1~2 h 内缓慢漂移 1 s，用户无感知。  
   - JVM：Oracle JDK 8u60+ 支持 **leap-second smear**（Google 方案：24 h 内分散 ±0.5 s）。

2. **金融交易**  
   - 交易所普遍 **提前 10 分钟停止撮合**，跳秒后重启；  
   - 高频策略需 **smear 或暂停**，防止 `23:59:60` 无法解析导致异常。

3. **电信/5G**  
   - OFDM 符号、帧边界依赖 **纳秒级 TAI**；基站内部用 TAI，对外显示 UTC，跳秒时 **帧计数续增 1 s**。

4. **航天/卫星**  
   - GPS 星载原子钟广播 **GPS 时间（无闰秒）**，地面段提供 **UTC(GPS) 偏移**；  
   - 深空测距用 **TAI** 避免累积误差。

### 五、系统应对策略

| 模式 | 原理 | 优点 | 缺点 |
|---|---|---|---|
| **跳秒 (leap)** | 23:59:60 真实出现 | 与 UTC 完全一致 | 23:59:60 需特殊解析；日志/数据库可能报错 |
| **Smear（涂抹）** | 24 h 内缓慢漂移 ±0.5 s | 无 60 秒异常；代码零改造 | 期间 UTC-TAI 偏离 0.5 s；金融需容忍漂移 |
| **TAI 内部 + UTC 显示** | 内部计数器用 TAI，对外换算 | 永远单调；无跳秒 | 需维护偏移表；跨系统同步复杂 |

Google、AWS、Alibaba 公共云均采用 **24 h smear**；  
交易所、电信核心网多采用 **跳秒 + 提前停服**。

### 六、未来趋势：闰秒去留？

- **ITU-R 第 7A 工作组** 2015 年起讨论“**取消闰秒**”：  
  让 UTC 与 UT1 漂移，不再插入闰秒，**彻底原子化**。  
- **决议时间**：2025 年 World Radiocommunication Conference (WRC-25) 将投票；若通过，**2035 年后不再插入闰秒**。  
- **漂移速度**：约 1 分钟/世纪，民用设备无感；天文、航天需独立维护 ΔT = UT1 − UTC 预报。
````

````
# 一、时间表示的“原子”概念

1. **Time-line（时间轴）**  
   数学上的一条实数轴，每一点对应一个物理瞬间。

2. **Epoch（历元）**  
   人为约定的“零点”，所有“时间戳”都是相对历元的**偏移量**。  
   - Unix：1970-01-01T00:00:00Z  
   - GPS：1980-01-06T00:00:00Z  
   - NTFS：1601-01-01T00:00:00Z  
   - Excel：1899-12-30T00:00:00Z（Windows 版）

3. **Unit（单位）**  
   秒(s)、毫秒(ms)、微秒(μs)、纳秒(ns)、皮秒(ps)、日(day)、百纳秒（NTFS）...

4. **Time-scale（时间标度）**  
   - TAI：国际原子时，无闰秒，连续。  
   - UTC：在 TAI 基础上插入闰秒，与地球自转同步。  
   - UT1：天文观测太阳，决定闰秒。  
   - 系统时间标度：通常跟踪 UTC，但内部可用 TAI 或单调时钟。

# 四、字符表示法（文本标准）

| 标准 | 实例 | 特征 | 用途 |
|---|---|---|---|
| ISO-8601 | `2024-06-01T08:30:45.123+08:00` | 扩展格式，可省分隔符 | 日志、JSON、REST |
| RFC-3339 | 同上（ISO-8601 子集） | 强制 4 位年、T、完整偏移 | 互联网协议 |
| RFC-1123 | `Sat, 01 Jun 2024 00:30:45 GMT` | 固定英文周月，GMT 结尾 | HTTP cookie/email |
| ANSI C asctime | `Sat Jun  1 00:30:45 2024\n` | 不含时区 | C/POSIX |
| W3C Note | 与 ISO-8601 一致 | 推荐毫秒、Z | Web 表单 |
| SQL literal | `TIMESTAMP '2024-06-01 08:30:45.123+08:00'` | 方言差异大 | 数据库迁移注意 |

**ISO-8601 细节补充**  
- 基本格式：`20240601T083045Z`（无分隔符）  
- 持续期：`P1Y2M3DT4H5M6S` 或 `P0001-02-03T04:05:06`  
- 时间间隔：`2024-06-01T08:00/2024-06-02T08:00`  
- 周日期：`2024-W22-6`（第 22 周周六）  
- 序数日：`2024153`（年内的第 153 天）

# 七、精度与误差来源

1. **闰秒**  
   UTC 插入 60 秒或跳秒，系统时钟可能回拨；用 TAI 或 smear 避免。

2. **时钟源**  
   - RTC（主板电池）  
   - NTP/PTP（网络）

3. **单调时钟**  
   `CLOCK_MONOTONIC`（Linux）、`System.nanoTime()`（Java）——**不关联历元**，只测间隔。

# 十、选型与最佳实践

1. **系统内部**  
   - 存储/日志：Unix 毫秒戳或 ISO-8601 UTC 字符串。  
   - 数据库：带时区的类型 (`TIMESTAMP WITH TIME ZONE`) → 存 UTC，读出按会话时区转。

2. **接口协议**  
   - REST/JSON：RFC-3339 字符串 (`2024-06-01T08:30:45.123Z`)。  
   - 二进制：Protobuf `google.protobuf.Timestamp`（秒+纳秒）、MessagePack 扩展类型 (-1)。

3. **显示给用户**  
   - 先转用户 `ZoneId`，再用地区格式 (`yyyy年M月d日 HH:mm`)。  
   - 避免用 12 小时制无 AM/PM 标记。

4. **夏令时与闰秒**  
   - 绝不手动加减 1 小时，交给库。  
   - 若需“绝对顺序”用单调时钟；若需“人类 LegalTime”用 UTC+TZ。

5. **精度选择**  
   - 金融交易：微秒级 + PTP 时钟。  
   - 分布式日志：毫秒戳足够。  
   - 科学测量：纳秒 + TAI 或 GPS 时钟。
````

````
### 2. 对程序意味着什么
- **本地时间不是连续的！**  
  2024-03-10 02:30 在美国东部**根本不存在**；11-03 01:30 会出现**两次**。
- **偏移会突变！**  
  同一时区 `America/New_York` 一年里先后给出 `-05:00` 和 `-04:00`。
- **存/传时间请用 UTC + 时间戳**，永远单调递增；**不要存本地字符串**。

### 3. Java 代码踩坑现场
```java

// 1. 春天“跳变”——02:30 不存在

Instant instant = Instant.now(); // 永远单调

### 5. 口诀 16 字
**春天拨快，秋天拨回；本地断档，UTC 不慌。**


夏令时（Daylight Saving Time, DST）的诞生并非自然现象，而是**人类为节约能源、延长傍晚活动光照**而主动调整的“人为时区偏移”。其根源可归结为三条主线：能源稀缺、工业作息扩张、政策工具化。

---

### 一、能源逻辑：煤炭与电灯的时代

1. **一次世界大战的煤炭危机**  
   1916 年德国率先推行 DST：夏季把时钟拨快一小时，傍晚多一小时自然光，**减少煤气灯和早期电力照明消耗**。  
   英国随即跟进，一年内节省煤炭约 2.5 万吨——DST 被验证为“战时廉价节能工具”。

2. **石油危机复活**  
   1973-1974 年中东石油禁运，美国国会紧急实施 DST，声称 **1974 年节省 1% 全国用电**（≈ 30 万桶油/年）。  
   此后欧洲、苏联、大洋洲陆续立法，DST 从“战时速决”变为“常态节能政策”。

---

### 二、工业作息：与“朝九晚五”同步

1. **固定工时制普及**  
   19 世纪末工厂实行统一打卡，**日出时间提前的夏季**出现“天亮已久却未开工”的浪费。  
   拨快一小时后，** sunrise → 07:00 变为 08:00**，工人起床即天亮，下班后仍有两小时日光，**休闲消费与零售销售额上升**（英美 1970s 统计增长 3-5%）。

2. **交通与赛事**  
   1920s 巴黎-伦敦夜间航班、1960s 电视体育直播均需“下班后日照”——DST 让** prime-time 节目**与自然光同步，减少赛场照明成本。

---

### 三、政策工具：立法、公投与弃用

1. **立法路径**  
   - 欧盟 1980 《Summer Time Directive》统一 DST 起止；  
   - 美国 2005 《Energy Policy Act》将 DST 延长至 8 个月；  
   - 俄罗斯 2011 年宣布“永久夏令时”，2014 年又退回永久标准时——显示其**可随时作为政治杠杆**。

2. **民意与弃用潮**  
   - 2018 年欧盟在线调查 460 万人，84% 支持废除 DST；  
   - 2019 年欧洲议会决议 **2021 年起各国可自选标准时或 DST**（因疫情推迟立法）。  
   - 2022 年起，**墨西哥、土耳其、阿根廷**已正式退出 DST，回归全年标准时。

---

### 四、现代争议：节能效果递减

1. **LED 普及**  
   高效照明使傍晚用电占比下降，多项 2010-2020 研究指出 **DST 节电 < 0.2%**，某些地区甚至**增加空调负荷**。

2. **健康与社会成本**  
   切换当日心脏病、交通事故上升 5-7%；跨境会议、航班、金融结算需额外调整窗口。

---

### 五、未来走向：逐步退场？

- **欧盟**：立法程序停滞，但多数国家倾向**全年保持夏季时**（即不再回拨）。  
- **美国**：2023 年《Sunshine Protection Act》尚未众议院表决，若通过将**永久 DST**（需各州同意）。  
- **全球趋势**：**弃用 > 新增**；DST 可能从“节能必需品”退为“地区特色”。

---

### 一句话总结

> 夏令时是**人类为省能源、适配工业作息**而发明的“拨快一小时”政策，**不是天文必要**；  
> 它在 20 世纪石油与煤炭危机中大放异彩，却在 21 世纪 LED 与健康成本面前逐渐褪色——**未来或永久定格在‘夏季时’，或被全年标准时取代**。
````

````
## 时间表示
带时区的时间可以通过多种方式表示，具体取决于使用场景和需求。以下是几种常见的表示方法：

### 1. **ISO 8601 格式**
ISO 8601 是国际标准，用于表示日期和时间，支持带时区的时间表示。格式如下：
```
YYYY-MM-DDTHH:MM:SS.sssZ
```
- `YYYY-MM-DD`：表示日期（年-月-日）。
- `T`：日期和时间的分隔符。
- `HH:MM:SS.sss`：表示时间（时:分:秒.毫秒）。
- `Z`：表示 UTC 时间（零时区偏移）。
- `±HH:MM`：表示时区偏移（相对于 UTC 的差值）。

**示例：**
- UTC 时间：`2024-06-27T14:30:00Z`
- 北京时间（+08:00）：`2024-06-27T22:30:00+08:00`
- 纽约时间（-04:00）：`2024-06-27T10:30:00-04:00`

### 2. **RFC 3339 格式**
RFC 3339 是基于 ISO 8601 的扩展，专门用于互联网协议。它对时间的精度和时区表示有更严格的要求。格式与 ISO 8601 类似：
```
YYYY-MM-DDTHH:MM:SS.sssZ
```

**示例：**
- `2024-06-27T14:30:00Z`（UTC）
- `2024-06-27T22:30:00+08:00`（北京时间）

### 3. **RFC 2822 格式**
RFC 2822 格式常用于电子邮件头部，包含星期、月、时区等信息：
```
Day, DD Mon YYYY HH:MM:SS +/-HHMM
```

**示例：**
- `Tue, 27 Jun 2024 22:30:00 +0800`（北京时间）

### 4. **自然语言表示**
在非技术场景中，带时区的时间可以用自然语言表示：
```
YYYY年MM月DD日 HH:MM:SS 时区
```

**示例：**
- `2024年6月27日 22:30:00 北京时间`
- `2024年6月27日 10:30:00 纽约时间`

### 5. **编程语言中的表示**
在编程中，带时区的时间通常通过特定的日期时间类型来表示，例如：

#### **Python**
```python
from datetime import datetime, timezone, timedelta

# UTC 时间
utc_time = datetime(2024, 6, 27, 14, 30, 0, tzinfo=timezone.utc)
print(utc_time.isoformat())  # 输出：2024-06-27T14:30:00+00:00

# 北京时间（+08:00）
beijing_offset = timedelta(hours=8)
beijing_time = datetime(2024, 6, 27, 22, 30, 0, tzinfo=timezone(beijing_offset))
print(beijing_time.isoformat())  # 输出：2024-06-27T22:30:00+08:00
```

#### **Java**
```java
import java.time.*;
import java.time.format.DateTimeFormatter;

// UTC 时间
Instant utcTime = Instant.parse("2024-06-27T14:30:00Z");
System.out.println(utcTime);  // 输出：2024-06-27T14:30:00Z

// 北京时间（+08:00）
ZoneId beijingZone = ZoneId.of("Asia/Shanghai");
ZonedDateTime beijingTime = ZonedDateTime.of(2024, 6, 27, 22, 30, 0, 0, beijingZone);
System.out.println(beijingTime);  // 输出：2024-06-27T22:30+08:00[Asia/Shanghai]
```

#### **JavaScript**
```javascript
// UTC 时间
const utcTime = new Date(Date.UTC(2024, 5, 27, 14, 30, 0));
console.log(utcTime.toISOString());  // 输出：2024-06-27T14:30:00.000Z

// 北京时间（+08:00）
const beijingTime = new Date(2024, 5, 27, 22, 30, 0);
console.log(beijingTime.toISOString());  // 输出：2024-06-27T14:30:00.000Z（内部存储为 UTC）
```

### 6. **数据库中的表示**
在数据库中，带时区的时间通常存储为 UTC，并通过时区转换显示为本地时间。

#### **SQL 示例**
```sql
-- 存储为 UTC
INSERT INTO events (event_time) VALUES ('2024-06-27 14:30:00');

-- 查询并转换为北京时间
SELECT CONVERT_TZ(event_time, '+00:00', '+08:00') AS beijing_time FROM events;
```

### 7. **HTTP 头部中的表示**
在 HTTP 协议中，时间通常用 RFC 1123 格式表示：
```
Day, DD Mon YYYY HH:MM:SS GMT
```

**示例：**
```
Tue, 27 Jun 2024 14:30:00 GMT
```

### 总结
带时区的时间可以通过以下方式表示：
1. **ISO 8601/RFC 3339**：`YYYY-MM-DDTHH:MM:SS.sss±HH:MM` 或 `YYYY-MM-DDTHH:MM:SS.sssZ`。
2. **RFC 2822**：`Day, DD Mon YYYY HH:MM:SS ±HHMM`。
3. **自然语言**：`YYYY年MM月DD日 HH:MM:SS 时区`。
4. **编程语言**：使用内置的日期时间类型（如 Python 的 `datetime`、Java 的 `ZonedDateTime`）。
5. **数据库**：存储为 UTC，查询时转换为本地时区。
6. **HTTP**：`Day, DD Mon YYYY HH:MM:SS GMT`。

根据具体场景选择合适的表示方式即可！
````

```
太阳日的长度是人类测量时间的标准方式。传统上，太阳日被细分为24小时，每小时60分钟，每分钟60秒，形成一个86400秒的一天。

现代计时系统基于原子钟，其定义的国际单位制（SI）秒与铯原子的跃迁频率精确对应。国际单位制秒的长度被定义为接近一天的86400分之一。

遗憾的是，随着地球自转，一天的时长会有所变化。此外，随着时间推移，由于地球自转速度逐渐减缓，平均每天的时长也在持续延长。因此，2012年太阳日的实际时长会略长于86400国际单位制秒。任何特定日期的实际时长以及地球自转减速的程度都无法预测，只能通过测量来确定。UT1时间尺度虽然能准确反映一天的时长，但其数据只能在一天结束一段时间后才能获取。

UTC时间尺度采用标准化方法，将UTC1中的所有零头秒数整合为整秒，即所谓的闰秒。闰秒的增减取决于地球自转的变化。因此，UTC允许一天包含86399或86401个国际单位制秒，以确保昼夜与太阳保持同步。

现代UTC时间标准于1972年正式确立，首次引入了整数闰秒的概念。1958至1972年间，UTC标准的定义较为复杂，不仅包含次秒级的微调，还对标准秒的长度进行了调整。截至2012年，学界正就UTC标准的重新修订展开讨论，可能涉及取消闰秒或引入其他调整方案。
```

### java.time包核心时间类及其API

`java.time`包的时间`API`中，我们可以将所有的类分为`3`部分：

1. 时间点表示：`Instant`用于表示时间线上的时间点，此类的底层一般用于时间戳的表示（即自1970年1月1日到现在经过了多少秒）当需要将此类转为具体的年月日时间时（特别涉及到时区），通常此类表示的时间和`UTC+0`对齐，即基准`UTC`时间、`Duration`（表示时间刻的类，比如表示3.5秒，6小时等）、`Period`（基于日期刻的类，比如表示3天，2年，4个月等）
2. 具体日期时间类表示：`LocalDate`代表区域日期、`LocalTime`代表区域时间、`LocalDateTime`代表区域日期时间、`ZonedDateTime`代表特定时区日期时间、`OffsetDateTime`代表`UTC`偏移日期时间、`OffsetTime`代表`UTC`偏移时间
3. 日期时间单位类：`DayOfWeek`（表示一周7天单位，比如星期一，星期二等）、`Month`（表示月份单位，比如一月，二月等）、`MonthDay`、`Year`、`YearMonth`、`ZoneId`、`ZoneOffset`、`ZoneRegion`等

还有其他类似于`Clock`这样的类，这些类提供了系统的底层时钟支持，这样的类我们也自行归类一类。

另外需要注意，`Duration`和`Period`实际上最长用于时间计算而非时间点表达，时间点表达`Instant`足够。
